01 — Introduction

02 — MCP

Model Context Protocol — Flutter-Skill

MCP is a standard that lets Claude connect to external tools. In our setup, we use flutter-skill — an MCP server that connects Claude directly to your running Flutter app on a real device.

🔌

What flutter-skill enables

  • Live UI inspection — Claude sees every widget on screen
  • Automated interaction — tap buttons, type text, scroll lists
  • Real device QA — test on your actual phone, not simulator
  • VM Service link — connects via Flutter's Dart VM URL
⚙️

How it's discovered

.mcp.json at project root — Claude Code auto-loads it on every session. No manual setup after first install.

.mcp.json (our real config)
{
  "mcpServers": {
    "flutter-skill": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-flutter-skill",
        "server"
      ]
    }
  }
}

03 — Hooks · Real Configuration

Hooks settings.json

All hooks live in .claude/settings.json. Claude Code reads this on startup — no code changes needed, just config.

  • "matcher": "Bash" — fires on every shell command
  • "matcher": "Write|Edit" — fires on every file write
  • Hook gets full tool input as JSON on stdin
  • exit 0 = allow  |  exit 2 = block
  • PostToolUse hooks are always informational — cannot block
Secret patterns lib:
_secret_patterns.sh is sourced by every guard hook. Add a new pattern once → all hooks get it automatically.
Manual scans:
bash .claude/hooks/pre_commit.sh
bash .claude/hooks/scan_git_history.sh --fix
.claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command",
          "command": "bash .claude/hooks/pre_bash_git_guard.sh"
        }]
      },
      {
        "matcher": "Write|Edit",
        "hooks": [{ "type": "command",
          "command": "bash .claude/hooks/pre_edit_guard.sh"
        }]
      }
    ],
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{ "type": "command",
        "command": "bash .claude/hooks/post_write.sh"
      }]
    }],
    "Stop": [{ "hooks": [{ "type": "command",
      "command": "bash .claude/hooks/on_stop.sh"
    }]}]
  }
}
pre_edit_guard.sh (simplified)
#!/bin/bash
source .claude/hooks/_secret_patterns.sh
FILE=$(cat | python3 -c "import json,sys; print(json.load(sys.stdin).get('path',''))")
FORBIDDEN=(".env" "*.jks" "env.g.dart" "google-services.json")
for p in "${FORBIDDEN[@]}"; do
  [[ "$FILE" == *"$p"* ]] && echo "❌ Blocked: $FILE" && exit 2
done
exit 0
04 — Skills · Our qa_test

Skills — Reusable AI Protocols

A Skill is a markdown file that defines a step-by-step protocol Claude follows when invoked. You invoke it with /qa_test — Claude reads .claude/skills/qa_test.md and acts as a Senior QA Engineer.

1
Device Discovery & LaunchRun flutter devices → find device ID → launch_for_testing.sh starts app → captures Dart VM URL
2
Connect flutter-skill MCPLinks Claude to the running app via VM URL → MCP now has eyes on the device
3
Semantic UI Mappingsnapshot + inspect_interactive → Claude maps every tappable & typeable element
4
Edge-Case Test MatrixEmpty form submit · 200+ char input · 🔥DROP TABLE; input · Keyboard overlap · Fast double-tap
5
Bug Report → STOPStructured markdown report with trigger steps → asks "Which bugs should I fix?" → waits for developer approval
.claude/skills/qa_test.md (excerpt)
# /qa_test — Senior QA Automation Protocol

## Phase 1: Device Discovery
1. Run `flutter devices` → identify device_id
2. Run `bash .claude/scripts/launch_for_testing.sh {device_id}`
   - This starts Flutter, captures VM URL
   - VM URL saved to `.claude/tmp/vm_url.txt`
3. Connect flutter-skill MCP to VM URL

## Phase 2: UI Mapping
- Call `snapshot` → get full widget tree
- Call `inspect_interactive` → list all:
  - Tappable elements (buttons, list tiles)
  - Typeable elements (text fields)
  - Scrollable containers

## Phase 3: Edge Case Matrix
| Test             | Action               | Check                   |
|------------------|----------------------|-------------------------|
| Empty submit     | Tap submit (no data) | Validation messages shown |
| Long input       | Paste 200+ chars     | No overflow crash       |
| Special chars    | Type `🔥DROP TABLE;` | No crash/escape issue   |
| Keyboard overlap | Tap bottom field     | Submit button still visible |
| Double tap       | Tap submit x2 fast   | No duplicate API calls  |

## Phase 4: Report & STOP
Output structured bug report with:
- Bug description
- Exact trigger sequence
- Suspected root cause

**DO NOT write any fix yet.**
Ask: "Which bugs should I resolve using ssl_cli architecture?"
Only proceed after explicit developer approval.

06 — Sub-Agents · Adding to Our Orchestration

Sub-Agents — Parallel Intelligence

Currently our setup uses one Claude session (one agent). Sub-agents mean spawning multiple Claude instances in parallel — each specialized. Here's how we could extend our orchestration:

CURRENT (single agent)
🧠 Claude Code (single)
does everything sequentially
reads rules → scaffolds → writes code → tests
⏱ Takes longer but simple setup
EXTENDED (orchestrator + sub-agents)
🧠 Orchestrator Claude
"Add payment history feature"
📋 Domain Agent
entity + usecase
🗄️ Data Agent
model + repo
📱 UI Agent
page + provider
🧪 QA Agent
/qa_test skill
⚡ All run in parallel → results merged
💡

Simple real-life example: Imagine your team lead says "build login". Instead of one Claude doing UI → API → tests one by one, the orchestrator splits the task: UI agent writes the Flutter widget while Domain agent writes the entity and use case at the same time. The orchestrator waits, then wires them together. Like having 4 junior devs working on the same feature simultaneously.
